# 180K 软匹配与连续概率场采样优化（2026-11-08）

## 当前结论与统一入口

推荐 `from fpsgen.vggi.point_transport import match`；旧 `soft_flow.match` 同步转向此实现。
返回连续软端点，保持源点行顺序；没有 GT 硬指派、重排、argmax 或最近邻吸附。
默认 FP32 `[N,3]` / `[B,N,3]`、K32、ε=(0.02,0.005,0.002)、λ=50、
3 次坐标更新、每次 30 次 Sinkhorn、步长0.9、去偏自项。每次坐标更新均重新寻找当前 KNN。
同 batch 的每个场景独立建树和求解，坐标完全重叠也不混场景。

这次不改变目标函数、迭代次数或近邻个数，未启动 Point Flow 训练，未运行 LiDiff。
GPU2 上的概率场训练未被本轮操作停止或修改。实验只使用 GPU3 RTX3090。

## 匹配耗时与瓶颈

旧 batch 的图构建约占69%，GPU已经被单场景充分占用。扩大batch没有空闲算力可成倍利用。
三项工程实验：

1. 双向 KNN 并集从全局64位边键排序去重改为每行ID排序、二分判重、计数及CSR/CSC scatter。
   保留完全相同的边和FP32距离，减少大规模临时数组；单独约快3%–4%。
2. 测叶大小32/64/128/256/512/1024，单帧耗时分别约386/341/303/287/279/293 ms；继续使用512。
3. 保存上一轮邻居ID，在更新后的坐标上重新计算这些K个真实候选的最大距离，用作新搜索的合法上界。
   BVH仍遍历所有可能更近的区域，候选发生变化时可找到新邻居。不是固定图、固定半径或近似KNN。
   距离上界带浮点裕量，测试与无上界搜索的邻居ID一致。

完整匹配时间：每场景180,000点、预热一次、五次新旧交错调用的中位数。
包含所有图构建、迭代、坐标更新和诊断回传；不含JIT、磁盘IO、H2D、采样和CPU质量评价。

|Batch|上一版batch / s|新默认 / s|加速比|新版本每场景 / ms|
|---:|---:|---:|---:|---:|
|1|0.2922|0.2289|1.28×|228.9|
|2|0.5499|0.4511|1.22×|225.5|
|4|1.0921|0.8867|1.23×|221.7|

B4场景为00_000500、00_001000、01_000500、00_000500，第四项刻意重复，用于检验隔离，不能当作四个独立场景。
新版本B4图构建约554 ms，求解约334 ms；再次优化优先考虑KNN遍历/访存，而非半精度坐标。
相对更早旧逐帧版本的历史1.302 s约快1.47倍；这不等于“batch自身提升1.47倍”。
当前尚未证明稳定达到用户希望的1.5倍，不能混淆基线。

### 同轮区分batch收益与算法收益

相同B4输入、四种路径预热后交错运行五次，结果如下：

|路径|整批中位耗时 / s|PyTorch峰值已分配 / GiB|
|---|---:|---:|
|旧逐帧|1.2983|1.029|
|上一版并行batch|1.0944|2.195|
|新算法逐帧|0.8954|0.730|
|新算法并行batch|0.8884|2.840|

新batch相对上一版batch约1.23倍，相对旧逐帧约1.46倍；**新算法本身逐帧与并行batch仅差约0.8%**。
主要收益来自算法工程优化，并非batch本身的倍增。无排序并集预分配2BNK边容量，
以及保存上轮邻居，会增加batch峰值显存；B4约2.84GiB，相比上版约2.20GiB。
若显存紧张，推荐相同新算法逐帧，耗时约0.895s而峰值约0.73GiB；不会切换成旧求解器。

## 连续概率场采样

目标保持 `rho(x)=(sum_j a_j B3_j(x))²`，不是把带符号系数当混合权重。
每个基础体素用邻近5³节点最大绝对振幅的平方作保守包络；在该体素内抽均匀点，
计算最多64节点的真实连续振幅后平方，再按rho/包络接受。没有阈值、额外Gaussian或体素中心近似。

CUDA改动：

- 三层256路FP32条件CDF替代一条数百万元素的全局前缀和，减轻小概率被大前缀吞掉的问题。
- 每个输出点有独立Philox流，独立完成拒绝采样；不按“谁先完成”抢占前180K名额。
- 统一缩放振幅避免包络平方溢出，比例在抽样中抵消；FP32包络含1e-5数值裕量。
- 超出拒绝预算或违反包络直接报错，不返回不足180K的部分点云。
- Gram状态支持 `codec.decode_cuda(q)`：三轴带状三角回代，状态和振幅无需往返CPU。
  固定几何的codec应复用，首次建立Gram因子的成本不计入每帧GPU解码。

三帧均采样精确180,000点。GPU采样列为包络/CDF已准备后的三种种子中位数，CPU为一次参考采样：

|场景|CPU参考 / ms|GPU采样 / ms|GPU实测接受率|由Gram质量预测接受率|
|---|---:|---:|---:|---:|
|00_000500|1138.4|0.758|0.329179|0.329114|
|00_001000|1127.0|0.715|0.322010|0.321907|
|01_000500|1012.9|0.647|0.348088|0.348420|

CPU使用FP64参考密度评价，GPU为FP32，CPU/GPU随机数序列也不同，不能声称逐点一致。
小网格独立Gauss积分的空间分布测试、接受率检验、符号不变性和种子复现均通过。
真实三帧接受率与由Gram总质量预测的接受率一致到Monte Carlo波动量级。
CPU/GPU差异的倍数主要来自串行numpy 64节点循环迁移到CUDA，不能理解为同一CUDA算子的千倍加速。

### 端到端热启动：00_000500

固定q、GT已在GPU，复用codec，测量解码→包络/CDF→180K采样→软匹配。
首次调用总计约0.797 s（含匹配模块首次加载）；下面是随后三次中位数：

|阶段|耗时 / ms|
|---|---:|
|Gram GPU解码|1.292|
|构建采样包络/CDF|1.186|
|180K连续采样|0.796|
|新默认软匹配|222.757|
|总计|226.012|

## 使用与复现

```python
from fpsgen.vggi.point_transport import match
from fpsgen.vggi.field_generation.sample_cuda import CUDAFieldSampler

# amplitude: FP32 CUDA [X,Y,Z]，原点和步长来自文件合同。
sampler = CUDAFieldSampler(amplitude, origin, spacing)
source, sample_info = sampler.sample(180000, seed=20261107)
endpoint, match_info = match(source, gt_xyz)  # 均为FP32 CUDA [180000,3]
# batch: match(source_BN3, gt_BN3)，当前要求所有场景等点数。
```

从Gram缓存文件直接导出：

```bash
CUDA_VISIBLE_DEVICES=3 python -m fpsgen.vggi.field_generation.sample \
  --cache /path/to/frame.npz --output /path/to/samples.npy --device cuda
```

参考CPU模式显式 `--device cpu`；CLI默认CUDA。Python `load_cache` 保留CPU默认以保证历史参考实验不变，
可用 `load_cache(path, device='cuda')`。网络推理后应直接复用codec调用 `decode_cuda(q)`，避免落盘再读取。

复现实验（真实场景缓存/inputs.npz需在服务器准备，未上传）：

